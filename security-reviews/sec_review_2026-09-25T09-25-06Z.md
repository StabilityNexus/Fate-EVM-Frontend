## Scope

Full-repository review of **Fate-EVM-Frontend** at commit `e2bd507d479dc704041cfefe0d213bae41698428` (`main`). Scope: `src/` (about 19,500 lines of TypeScript and TSX across app routes, components, hooks, lib, and utils), plus `next.config.mjs`, `env.example`, `.gitignore`, and the four workflows under `.github/workflows/` as configuration context. `node_modules/`, `public/`, and `*.test.ts` files were not reviewed.

Project type detected: **Frontend (Next.js / React / Tailwind)**. Next.js 15 with `output: "export"` (static site, deployed to GitHub Pages by `nextjs.yml`), React 19, wagmi 2 + viem 2, RainbowKit for wallet connection, TanStack Query, IndexedDB via `@aossie-org/idb-backup` for local portfolio history. There are no API routes, Server Actions, middleware, or cookies, so the server-side items of the frontend checklist (SSRF, CSRF, IDOR, server-side injection, secrets in `getStaticProps`) do not apply. The trust boundary is the user's browser plus their wallet: the app reads chain state over public RPC and asks the wallet to sign transactions it constructs.

Context held during the review: the oracle allow/deny filter (#144, not yet on `main`) is a listing filter for Explore only, and the direct `/pool?id=` route is intentionally unfiltered. Estimates are client-side mirrors of contract math and the chain is authoritative. `NEXT_PUBLIC_PROJECT_ID` is the WalletConnect (Reown) project id, which is public by design.

## Findings

### Finding 1: A third-party widget script runs with full page privileges on the trading page — `src/components/ui/TradingViewWidget.tsx:53`

- Severity: Low
- Confidence: 0.70
- Category: third_party_script
- Description: The pool page injects `https://widgets.coingecko.com/gecko-coin-price-chart-widget.js` as a live `<script>` element into the document. That script executes in the app's origin with the same access as first-party code: it can read React state, patch `window.ethereum` and the wagmi client, alter the arguments passed to `writeContract`, or rewrite what the UI shows before the wallet prompt. The site is a static export with no response headers, and no `<meta http-equiv="Content-Security-Policy">` is set, so nothing constrains what that script (or anything it loads) may do. There is no Subresource Integrity hash and none is practical for a vendor-updated widget. This is reported at the confidence floor because exploitation requires a compromise of CoinGecko's widget host or the path to it, not of this codebase; it is listed because the page where it runs is the one where users approve token spending and sign trades.
- Exploit Scenario: The widget host, its CDN, or a DNS/BGP path to it is compromised. The malicious script waits for a `buy` or `approve` flow, swaps the `receiver` argument or raises the approval amount before `writeContract` is called, and leaves the rendered UI unchanged. The wallet shows the real calldata, but most users confirm what the dapp displayed.
- Recommendation: Isolate the widget in a sandboxed `<iframe sandbox="allow-scripts" srcdoc="...">` (or an `<iframe>` pointing at a static widget page under `public/`) so it has no access to the parent document, and add a `<meta http-equiv="Content-Security-Policy">` in `layout.tsx` that limits `script-src` to `'self'` plus the wallet SDK origins and `connect-src` to the RPC and WalletConnect hosts. If the chart is not worth an iframe, drop it: a link to the CoinGecko page conveys the same information with no script in-origin.

## Notes

### Note 1: A restored backup is trusted after a wallet match, not authenticated — `src/lib/backup/portfolioBackup.ts:177`

- Category: accepted-risk
- Observation: `readBackupFile` validates the JSON's shape and `restorePortfolioBackup` refuses files whose recorded wallet is not the connected one, but the recorded wallet is an ordinary field in the file. Anyone who knows a victim's public address can craft a "backup" naming it. If the victim imports that file, the portfolio page will display fabricated positions, trades, and pool links (`/pool?id=<attacker pool>`), which is a lure toward a pool with a creator-chosen oracle. Nothing in the file reaches a transaction, `innerHTML`, or a cross-origin URL; the pool route re-validates the address and reads live chain data.
- Rationale: The wallet check was designed to stop users mixing their own wallets' data (the code comment says so), not to authenticate a file; import is a deliberate user action on the Settings page with a confirmation step. Signing backups would need a key the app does not hold. The residual risk is a phishing lure inside the user's own browser, which is a user-education matter. Not a finding.

### Note 2: `dangerouslySetInnerHTML` and `innerHTML` are used only with first-party strings — `src/app/layout.tsx:98`

- Category: design-observation
- Observation: The two `dangerouslySetInnerHTML` uses in `layout.tsx` and the one in `About.tsx` inject a fixed theme bootstrap script and JSON-LD built from literals via `JSON.stringify`. The `innerHTML` write in `TradingViewWidget.tsx:59` interpolates `coinId`, which is derived from `getPriceFeedName()`: a lookup in a static address-to-name table that returns the literal `"Unknown"` for anything unlisted. No chain-sourced or user-sourced string reaches any of them. Pool names, symbols, and addresses read from the chain (including from creator-controlled oracles) are rendered through JSX, which escapes.
- Rationale: Traced to confirm the XSS checklist items are clean; recorded so the next reviewer does not repeat the trace. Not a finding.

### Note 3: Every pool address from the chain is validated before use, and approvals are exact — `src/app/[pool]/InteractionClient.tsx:907`

- Category: design-observation
- Observation: The `?id=` query parameter is accepted only if `isAddress()` passes; the Hero modal and the Explore "use pool" path apply the same check before `router.push`. Token approvals in both the trade flow (`InteractionClient.tsx:532`) and pool creation (`CreateFatePool.tsx:372`) request the exact amount, never `maxUint256`, and creation skips the approval when the existing allowance suffices.
- Rationale: Recorded as verified good practice relevant to the wallet trust boundary. Not a finding.

### Note 4: `pull_request_target` is used with a write token but without checking out PR code — `.github/workflows/label-merge-conflicts.yml:5`

- Category: design-observation
- Observation: The merge-conflict labeler runs on `pull_request_target` with `pull-requests: write`, which is the trigger class behind "pwn request" attacks. The job never checks out or executes anything from the PR; it only runs `eps1lon/actions-label-merge-conflict@v3` with the default token. The remaining exposure is the action itself being pinned to a mutable tag rather than a commit SHA.
- Rationale: No PR-controlled code path exists, so this is not exploitable through a pull request; SHA-pinning is a hardening step the Scorecard workflow already tracks. Not a finding.

## Limitations

**Standing limitations**

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or traced at runtime, so timing-dependent, load-dependent, or infrastructure-dependent issues cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails built into some models can cause a real vulnerability to be softened, generalized, or left out rather than reported in exploit-level detail, and training-data bias can make some vulnerability classes easier for a model to recognize than others. Treat this report as a floor on what a full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to a very recently disclosed CVE or library advisory may not be recognized as such.

**Review-specific limitations**

- The three largest files (`src/app/portfolio/page.tsx`, 2,750 lines; `src/app/[pool]/InteractionClient.tsx`, 1,903 lines; `src/app/explorePools/page.tsx`, 860 lines) were reviewed by targeted reads around every sink and trust-boundary crossing found by search (query parameters, storage reads, `innerHTML`, `window.open`, `approve`, external URLs, `dangerouslySetInnerHTML`), not line by line. Pure rendering and data-shaping code in them was not read in full.
- `node_modules/` was not reviewed; the security of `@rainbow-me/rainbowkit`, `wagmi`, `viem`, `@aossie-org/idb-backup`, `react-markdown`, and `next` was assumed. No dependency audit (`npm audit`) was run.
- The hosting layer (GitHub Pages) was not reviewed; the absence of security response headers is inferred from the static-export configuration, not observed.
- `src/utils/ethersProvider.ts` reads two `NEXT_PUBLIC_*` variables that `env.example` does not define and has no callers in `src/`; it was treated as dead code and not evaluated further.
